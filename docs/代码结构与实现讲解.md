## 四、逐层拆解

### 4.1 界面层：`activity_main.xml` 为什么是三段式

```
ConstraintLayout (id=main, 背景 宣纸色)
├── LinearLayout (id=header)         朱红渐变头，约束 top
│     ├── TextView  "遗小课" 24sp 粗体 白色
│     └── TextView  slogan 13sp
├── HorizontalScrollView (id=chip_scroll)  约束在 header 下
│     └── LinearLayout 横排 5 个 TextView（style=@style/YxChip）
├── RecyclerView (id=project_list)   上边贴 chip_scroll 底，下边贴父底
└── TextView (id=empty_view)         与 RecyclerView 区域重叠居中，默认 gone
```

三个设计点：

1. **为什么用 ConstraintLayout 而不是 LinearLayout 垂直排列**：RecyclerView 要"占满剩余高度"，LinearLayout 得给它 `weight=1`；而空态要和列表区域重叠居中，LinearLayout 做不到，ConstraintLayout 用四条约束一放就行。
2. **`HorizontalScrollView` 包分类条**：5 个标签在窄屏（如 5.0 英寸）放不下，横向可滚。第 5 个"民俗"在截图里被切了一半，这就是横滚条的作用，不是 bug。
3. **空态独立成一个 TextView**，跟列表做同一区域约束、默认 `gone`，由代码切 `VISIBLE/GONE`——这是"如何控制 UI 界面"知识点最直接的落点。

### 4.2 边到边（EdgeToEdge）与 insets

`MainActivity.java:51` 调 `EdgeToEdge.enable(this)`，作用是把窗口铺到状态栏和导航栏后面（Android 15 起强制，早版本也可主动开）。副作用是内容会被状态栏压住，所以要 `applySystemBarInsets()` 把系统栏高度补成根布局 padding（61-66 行）。

**第二位容易踩的点**：主题锁的是 Light，但系统可能处于深色模式，`EdgeToEdge` 默认会按系统模式决定状态栏图标颜色 → 深色系统下会出现"浅色背景 + 白色图标 = 看不见"。所以第 68-69 行强制 `setAppearanceLightStatusBars(true)`。

### 4.3 列表层：RecyclerView 三件套

| 角色 | 代码 | 职责 |
|---|---|---|
| LayoutManager | `new LinearLayoutManager(this)` | 决定"竖排、每项一行、怎么回收" |
| Adapter | `ProjectAdapter` | 决定"有多少项、每项长什么样" |
| ViewHolder | `ProjectViewHolder` | 缓存 `findViewById` 的结果，避免每次滑动重复查找 |

**复用机制**（必被追问）：

- `onCreateViewHolder` 只在"需要新视图"时调用（一屏能显示 5 张卡片，就只创建 6 个左右），之后滑出屏幕的 View 会被回收；
- `onBindViewHolder` 每项进入屏幕都要调，所以**所有会变的数据必须在这里重新赋值**，否则会出现"滑走再滑回，卡片显示的是别人的名字"。

代码里 `bind()` 把 5 个 TextView 全部重新 `setText`，正是这个原因。`ProjectViewHolder` 声明成 `static`，是为了不持有外部 Adapter 引用（非静态内部类会隐式持有，容易造成内存泄漏）。

**回调接口**（`ProjectAdapter.java:25-27`）：Adapter 不自己做跳转，只把"哪个项目被点了"抛给 Activity。这样做的好处是同一个 Adapter 将来可以在"我的收藏"页面复用，跳转行为不同但不用改 Adapter。

**已知技术债**：`notifyDataSetChanged()`（`MainActivity.java:115`）会全量重绘，8 条数据无所谓，数据上百条时应该换 `DiffUtil`。答辩时如果被问性能优化，这是标准答案之一。

### 4.4 模型层：`Project` 的取舍

- 字段全部 `final`：项目数据是"读"出来的，不需要中途改，改成 `final` 后编译器帮你保证不会被意外覆盖（进度、收藏这些**可变状态不放在 Project 里**，将来放在 `study_record` / `favorite` 表）。
- 分类用 `String` 常量而不是 `enum`：因为分类要直接写进 SQLite 的 `category` 字段、也要直接当筛选条件比较，用字符串少一层 `name()` 转换。（代价是写错不报错，属于权衡。）
- `getCoverText()`（54-56 行）返回项目名首字：现在没有图片资源，用它做封面占位；S5b 有 `cover_img` 后用 `ImageView` 替换，这个方法就可以删掉。

### 4.5 资源层：状态由选择器驱动，不在代码里写颜色

分类标签的"选中变红"是这么实现的：

```
bg_chip.xml      <selector>  state_selected=true → 朱红实心圆角；否则 → 米色
chip_text.xml    <selector>  state_selected=true → 白色文字；否则 → 墨灰文字
```

代码里只做一件事：`chipViews.get(i).setSelected(i == index)`（`MainActivity.java:100-102`）。**颜色变化完全由 XML 选择器完成**，Java 里没有一行 `setBackgroundColor`。

这样做的价值：换配色只改 `colors.xml`，不用碰活动代码；答辩讲"界面设计与控制"时，这是"数据驱动界面"的现成例子。

### 4.6 筛选逻辑放在 Activity 而不是 Adapter

`applyFilter()`（107-117 行）的做法是：清空 `shownProjects` → 遍历 `allProjects` 按 `currentCategory` 过滤 → 通知刷新 → 顺便切空态。

为什么不让 Adapter 自己提供 `filter()`：因为 Adapter 一旦持有"全量数据 + 过滤条件 + 当前结果"三份状态，逻辑就会耦合；现在 Adapter 只是个"听话的展示器"，谁传什么就显示什么，复用到收藏页、搜索页时零改动。

**分类的顺序约定**（31-38 行注释）：`CATEGORIES` 数组的顺序必须和 XML 里 5 个 chip 的声明顺序一致，靠的是 `chipViews.add(...)` 的添加顺序（73-77 行）。这是"位置约定"，将来如果分类要动态生成，就该改成 `Map<TextView, String>` 而不是靠顺序。

### 6.3 第二步：数据库层（S5b 前半，约 3 天，最关键）

建表 SQL 已在初设文档 5.4 定稿，这里只讲落地顺序：

1. **`DBHelper` 继承 `SQLiteOpenHelper`**，`onCreate` 里执行三条建表 + 两个索引；`onConfigure` 里 `setForeignKeyConstraintsEnabled(true)`。
2. **首次导入**：`onCreate` 里读 `assets/projects.json` 批量插入。注意——`onCreate` 运行在调用 `getWritableDatabase()` 的线程，**不要在 `onCreate` 外面再套子线程**，否则容易死锁；如果导入耗时长，改成"onCreate 建表，导入单独一个方法在子线程调"。
3. **DAO 只做 SQL，不做界面**。统一返回 `List<Project>`，异常吞掉返回空列表并打日志。
4. **`ProjectDao.queryByCategory`** 与现在的内存过滤等价，切过来只要改 `applyFilter()` 一行。

DAO 接口契约（组员并行开发就靠这张表，先冻结再写实现）：

| 方法 | 返回 | 用途 |
|---|---|---|
| `ProjectDao.queryAll()` | `List<Project>` | 首页全量 |
| `ProjectDao.queryByCategory(String)` | `List<Project>` | 分类筛选（传 `null` 或 `"全部"` 表示不过滤） |
| `ProjectDao.search(String)` | `List<Project>` | F9 搜索，`LIKE '%kw%'` |
| `ProjectDao.queryById(int)` | `Project` | 详情页 |
| `FavoriteDao.isFavorite(int)` | `boolean` | 详情页按钮初始态 |
| `FavoriteDao.add(int)` / `remove(int)` | `int` | 收藏/取消，`INSERT OR IGNORE` |
| `FavoriteDao.queryFavorites()` | `List<Project>` | 我的页面收藏列表（JOIN） |
| `FavoriteDao.count()` | `int` | 我的页面汇总 |
| `StudyRecordDao.checkin(int, String)` | `long` | 打卡，`INSERT OR IGNORE`，返回 -1 表示今天已打过 |
| `StudyRecordDao.saveQuiz(int, String, int, int)` | `long` | 测验成绩，`INSERT OR REPLACE` |
| `StudyRecordDao.queryCheckedDates(String yyyyMM)` | `Set<String>` | 打卡日历 |
| `StudyRecordDao.queryCheckinDays()` | `int` | 累计打卡天数 `COUNT(DISTINCT checkin_date)` |
| `StudyRecordDao.queryStatus(int)` | `int` | 单项目进度：0 未开始 / 1 学习中 / 2 已掌握 |
| `StudyRecordDao.queryStatusMap()` | `Map<Integer,Integer>` | 列表批量状态（避免 N 次查询） |

> `queryStatusMap` 是个值得讲的设计：如果要给列表每张卡片显示进度，逐项查库是 N+1 查询，一条 `GROUP BY` 拿全部才对。

### 6.4 第三步：测验（S5b 后半，约 2 天）

题目建议**跟内容一起放 `assets/projects.json`**，结构：

```json
{ "id": 1, "name": "京剧脸谱",
  "quiz": [ { "stem": "京剧脸谱中红色通常代表？",
              "options": ["忠诚正义","阴险奸诈","刚正不阿","神怪"],
              "answer": 0, "explain": "红脸多表示忠勇侠义，如关羽。" } ] }
```

判分流程：用户选完 → 比对 `answer` → 累加得分 → 全部答完 → 写 `study_record`（`INSERT OR REPLACE`，同一天重测覆盖）→ 跳结果页展示得分和错题解析。

**两个必须讲的设计**：① 提交成绩用 `INSERT OR REPLACE` 而不是 `UPDATE`，因为"当天第一次测"时记录还不存在；② 进度取 `MAX(score/total)`，保证重测低分不覆盖历史最好成绩。

### 6.5 第四步：我的页面与打卡（S5b 尾，约 1.5 天）

我的页面 = 4 个数字 + 2 个入口（收藏列表、打卡记录）。4 个数字分别来自：

```sql
SELECT COUNT(*) FROM favorite;                                   -- 收藏数
SELECT COUNT(DISTINCT project_id) FROM study_record;             -- 学习中（至少学过）
SELECT COUNT(DISTINCT project_id) FROM study_record WHERE quiz_done=1
       AND quiz_score*1.0/quiz_total >= 0.8;                     -- 已掌握
SELECT COUNT(DISTINCT checkin_date) FROM study_record;           -- 累计打卡天数
```

## 七、技术债与坑清单

| # | 问题 | 影响 | 处理时机 |
|---|---|---|---|
| 1 | `Project` 缺 `id` | 详情页无法传参 | **立刻**（S5a 第一步） |
| 2 | 8 条数据硬编码在 Activity | 内容和代码耦合，组员改内容要动 Java | S5b 转 `assets/projects.json` + SQLite |
| 3 | `notifyDataSetChanged()` 全量刷新 | 数据量大时卡顿 | S6 优化项，答辩可讲 |
| 4 | 分类顺序靠数组与 XML 声明顺序对齐 | 增删分类容易错位 | 分类稳定后再重构 |
| 5 | 分类文案硬编码在 `Project` 常量里（中文） | 将来做多语言要改 | 可接受，写进"已知限制" |
| 6 | `minSdk 24` 的 SQLite 是 3.9.2 | **不能用 `ON CONFLICT ... DO UPDATE`**（UPSERT 要 3.24+），真机会抛语法错误 | 写库前确认，用 `INSERT OR REPLACE` |
| 7 | `EdgeToEdge` 下每个新 Activity 都要处理 insets | 漏处理会被状态栏遮挡 | 详情页创建时照抄 `applySystemBarInsets()` |
| 8 | 样式名不能带点（`Yx.Chip` 会被当父样式） | AAPT 链接失败 | 已修，新样式叫 `YxChip` 这种无点命名 |
