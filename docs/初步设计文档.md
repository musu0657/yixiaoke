## 一、项目简介与选题意义

### 1.1 项目概述

| 项 | 内容 |
|---|---|
| 产品形态 | 单机 Android APP，安装即用，无需注册与联网 |
| 目标用户 | 小学高年级至初中学生（10–15 岁），及陪同使用的家长 |
| 内容载体 | 8–12 个非遗项目的图文资料 + 工序步骤 + 小测验 |
| 核心闭环 | 浏览项目 → 看工序与传承人故事 → 做小测验 → 收藏/记录进度 → 打卡 |
| 技术路线 | Java + 原生 Activity/XML + SQLite 三表 + WebView 本地 HTML |
| 课程契合 | 覆盖课纲 11 条知识点，并补充 1 项自学技术点（自定义 View） |

产品的设计立场很明确：**不做"非遗百科"，做"非遗小课"**。百科解决"查到"，小课解决"学会"——所以每个项目都配有可判分的小测验和可见的学习进度，让学习过程有终点、有反馈。

### 1.2 选题背景：非遗传承的"青少年断层"

非物质文化遗产的传承依赖"人传人"，而当前面临的核心问题不是资料匮乏，而是**代际兴趣断层**：青少年能说出"非遗"这个词，却往往举不出一个具体项目，更不了解其工序与传承人。造成断层的原因有三个层面：

1. **内容层面**：现有非遗资料多为成人向的学术描述或宣传通稿，术语密集、篇幅长，超出中小学生的阅读耐受区间。
2. **形式层面**：图文长文、纪录片、线下展馆是主流载体，缺少"短时长、可交互、有反馈"的轻量形态，难以嵌入课间 5 分钟这类碎片时间。
3. **动机层面**：学习非遗缺少即时正反馈，不像游戏有等级与成就，青少年很难自发坚持。

因此，把非遗内容**降维**为适合青少年认知的卡片、工序图解和测验，并用进度与打卡提供正反馈，是一个有现实价值、且技术难度与课程要求相匹配的切入点。

### 1.3 选题意义

| 维度 | 意义 |
|---|---|
| 认知价值 | 用"一项目一小课"的粒度降低认知门槛，让青少年在 5–10 分钟内完成一次完整认知（认识 → 理解工序 → 验证掌握） |
| 传播价值 | 以可离线、可安装的形式把非遗内容带到没有网络条件的课堂与家庭场景，扩大触达面 |
| 课程价值 | 非遗是课纲推荐题目，且业务闭环天然覆盖"列表—详情—交互—存储—文件—多线程"全链路，知识点落点充足，不牵强 |
| 工程价值 | 一人主力 + 三人协作的团队结构，正好需要分阶段推进与 Git 留痕来保证可交付性，与课纲的"按软件工程分阶段"要求一致 |

### 1.4 设计目标与验收标准

初步设计阶段先锁定**可验收**的目标，避免后期"做完了但说不清完成度"：

| 编号 | 目标 | 可验收标准 |
|---|---|---|
| G1 | 核心闭环可演示 | 从首页点进任一项目，完成阅读 + 测验 + 打卡，全程无崩溃，耗时 < 5 分钟 |
| G2 | 内容规模达标 | 内置 8–12 个非遗项目，每个含历史渊源、工序步骤（≥4 步）、传承人故事、3–5 道测验题 |
| G3 | 知识点全覆盖 | 课纲 11 条知识点逐条有代码落点，答辩可现场指认 |
| G4 | 数据可靠 | 重复打卡不产生重复记录；卸载重装后内容自动重新导入 |
| G5 | 分阶段留痕 | Git 提交带阶段前缀，每个阶段有可见产物，可回溯 |

## 二、需求分析

### 2.1 目标用户画像

| 画像 | 特征 | 使用场景 | 对设计的影响 |
|---|---|---|---|
| P1 小学生（10–12 岁） | 识字量有限，注意力约 10 分钟，喜欢点按与即时反馈 | 课间、放学后，家长手机或平板 | 大字号、少文字、每屏一个信息点；测验选项不超过 4 个；操作只有点击与滑动 |
| P2 初中生（13–15 岁） | 有自主搜索能力，关注"我学会了什么" | 自习课、周末，自己的手机 | 需要进度与测验分数这类可量化反馈；允许更长文本与工序细节 |
| P3 家长 | 关注内容是否健康、是否耗费流量与时间 | 陪同使用、检查孩子学了什么 | 无广告、无社交、无联网；"我的"页面可一览学习与打卡情况 |

三类用户的共同点是：**都不愿意为学习类 APP 付出注册成本与学习成本**。因此产品不设登录、不做引导页，安装后 3 秒内必须看到第一屏内容。

### 2.2 核心痛点与需求推导

| 编号 | 痛点 | 具体表现 | 推导出的需求 |
|---|---|---|---|
| T1 | 内容太"重" | 非遗资料是长文与术语，青少年读不下去 | 卡片化摘要（一句话简介 + 难度标签），详情页分区折叠，工序图解化 |
| T2 | 学了没反馈 | 看完即忘，不知道自己掌握没有 | 每项目 3–5 道选择题即时判分，给出对错解析 |
| T3 | 坚持不下去 | 缺少目标感与成就感 | 学习进度三档状态 + 按天打卡记录，形成可视化积累 |
| T4 | 网络环境不保证 | 教室 Wi-Fi 不稳、家长不愿让孩子长时间联网 | 全离线：内容随 APK 打包，数据存本地 SQLite |
| T5 | 内容零散难找 | 找不到"我想看的那个" | 分类浏览，加分项补搜索与筛选 |

> **需求来源说明**：以上痛点由小组调研（竞品分析 + 现有资料分析）得出，调研原始材料将作为附录 A 并入定稿设计文档，本节结论与调研材料须一一对应，不可空口断言。

### 2.3 功能需求清单

| 编号 | 功能 | 优先级 | 验收标准 |
|---|---|---|---|
| F1 | 非遗项目列表 | 必做 | 卡片展示名称、分类、一句话简介、难度；分类切换后列表正确刷新 |
| F2 | 项目详情 | 必做 | 展示历史渊源、工序步骤、传承人故事；从列表点入并正确传参 |
| F3 | 小测验 | 必做 | 每项目 3–5 题，选完即时判分，展示得分与正确答案 |
| F4 | 收藏 | 必做 | 点击收藏写入 `favorite` 表，重复收藏不产生重复行，可取消 |
| F5 | 学习进度 | 必做 | 三档状态：未开始 / 学习中 / 已掌握，由学习记录聚合得出 |
| F6 | 打卡记录 | 必做 | 按日期记录，同一项目同一天仅一条记录 |
| F7 | 我的页面 | 必做 | 汇总展示收藏数、学习中/已掌握数、累计打卡天数 |
| F8 | 打卡日历 | 加分 | 月历视图标记打卡日，可切换月份 |
| F9 | 搜索与筛选 | 加分 | 按名称关键字检索、按分类筛选，结果为空时显示空态 |

### 2.4 非功能需求

| 编号 | 类别 | 要求 |
|---|---|---|
| N1 | 性能 | 冷启动 ≤ 2 s；列表滚动无明显掉帧；单次数据库查询 ≤ 100 ms |
| N2 | 兼容性 | minSdk 24（Android 7.0）及以上；适配 5.0–6.7 英寸主流分辨率；浅色主题固定，不随系统深色模式变化 |
| N3 | 可靠性 | 任何页面操作不导致崩溃；数据库操作异常有兜底提示；重复打卡/重复收藏幂等 |
| N4 | 可用性 | 正文字号 ≥ 16sp，可点击区域 ≥ 48dp；主要操作不超过两级页面 |
| N5 | 体积 | 安装包 ≤ 15 MB（含图片与本地 HTML 资源） |
| N6 | 合规性 | 不申请网络、定位、通讯录等无关权限；导出的数据文件仅写入应用私有外部目录 |

## 四、技术路线与架构选型

### 4.1 总体技术路线

采用经典的**三层架构**，层间单向依赖，界面层不直接写 SQL：

```
┌─────────────────────────────────────────────┐
│  界面层（Presentation）                      │
│  Activity + XML 布局 + RecyclerView Adapter  │
│  职责：渲染、事件接收、页面跳转与传参         │
└───────────────────┬─────────────────────────┘
                    │ 只调用业务方法，不拼 SQL
┌───────────────────▼─────────────────────────┐
│  业务/数据访问层（Domain & DAO）             │
│  ProjectDao / FavoriteDao / StudyRecordDao   │
│  职责：业务规则（判分、状态聚合）、SQL 拼装   │
└───────────────────┬─────────────────────────┘
                    │
┌───────────────────▼─────────────────────────┐
│  存储层（Persistence）                       │
│  SQLiteOpenHelper + SQLite（三张表）         │
│  assets/ 静态资源（图文、本地 HTML、种子数据）│
└─────────────────────────────────────────────┘
```

这样分层的直接收益：一是我一人主力开发时，组员可以只改界面层而不碰 SQL；二是后期若接服务器，只需替换 DAO 实现，界面层零改动。

### 4.2 技术选型决策表

| 决策点 | 选项 | 结论 | 理由 |
|---|---|---|---|
| 开发语言 | Java / Kotlin | **Java** | 课纲明确写 Android + Java；组员 Java 基础更好，协作成本低 |
| 界面方案 | 原生 Activity+XML / Jetpack Compose / Flutter | **原生 Activity + XML** | 课程知识点（布局、控件、监听、跳转）全部基于 XML 体系，换框架等于放弃知识点落点 |
| 数据存储 | SQLite / Room / SharedPreferences / 文件 | **SQLite（SQLiteOpenHelper）** | 课纲要求"数据库应用"；手写 SQL 能体现建表、约束、聚合查询等真实数据库能力，Room 会把这层遮蔽掉 |
| 富文本展示 | WebView / 原生 TextView | **WebView + assets 本地 HTML** | 同时覆盖"Web"知识点；本地 HTML 排版表达力强于 TextView；零服务器即离线可用 |
| 图片加载 | Glide / 原生 Drawable | **原生 Drawable + assets** | 项目为本地图片，无网络加载需求，不引入额外依赖 |
| 主题 | Material3 DayNight / Light | **Light（固定浅色）** | 国风暖色配色在深色模式下会失真，锁定浅色保证视觉一致性 |
| 构建 | AGP 9.3 + compileSdk 37（现状） | **维持现状** | 已在真实工程验证 `assembleDebug` 通过，不为了"教程常见"而主动降级 |

### 4.3 为什么选择本地 SQLite 而不是服务器

这是本项目的**核心架构决策**，从五个维度论证：

| 维度 | 本地 SQLite（选定） | 服务器 + 远程数据库（放弃） |
|---|---|---|
| 成本 | 零成本 | 需云主机/域名/备案，或至少一台常开的机器 |
| 可用性 | 安装即用，断网、飞行模式、教室无网均可用 | 网络异常即不可用，演示现场风险极高 |
| 数据特性 | 内容为**静态预置**（非遗资料），一次导入、只读为主 | 服务器更适合高频写入与多用户并发，本项目无此需求 |
| 课程契合 | 已完整满足"数据库应用"知识点：建表、约束、增删改查、聚合、事务 | 超出课纲要求，工作量与风险不对等 |
| 运维 | 无（用户数据在本地，卸载即清） | 需处理部署、备份、权限、并发与安全 |

**判定依据**：引入服务器只在满足以下任一条件时才值得——内容需要运营方频繁更新、需要多端同步、需要用户间互动。本项目三条都不成立，因此服务器属于**过度设计**。

**同时保留演进空间**（答辩时说明"未来可扩展"）：

1. DAO 接口化：所有数据访问经 `XxxDao` 接口，将来新增 `RemoteXxxDao` 即可切换数据源；
2. ContentProvider 或 Repository 作为唯一数据入口，界面层不感知来源；
3. WebView 层天然是未来接入在线内容（如"非遗小百科"在线版）的预留点。

### 4.4 关键技术难点的技术方案

| 难点 | 方案 | 风险控制 |
|---|---|---|
| 内容与代码解耦 | 非遗资料以 JSON/结构化数据放 `assets`，首次启动解析并写入 SQLite；用 `version` 字段支持后续覆盖导入 | 导入失败不覆盖已有数据，界面显示重试入口 |
| 打卡幂等 | 建表即用 `UNIQUE(project_id, checkin_date)`，写入用 `INSERT OR IGNORE` | 由数据库保证幂等，不依赖应用层判断，避免竞态 |
| 进度聚合 | 由 `study_record` 聚合：无记录=未开始；有记录但未通过测验=学习中；测验达标=已掌握 | 聚合逻辑集中在 DAO，一处修改全局生效 |
| 多线程 | 按月查询与 CSV 导出在子线程执行，结果经 `Handler` 回主线程刷新 UI | 统一封装 `runOnUiThread`/`Handler` 模式，禁止主线程查询 |
| 自定义工序步骤条 | 继承 `View`，`onDraw` 绘制节点与连线，暴露 `setCurrentStep()` | 先做静态进度展示，动画后置，避免阻塞主线 |
| 文件导出 | 写入 `getExternalFilesDir()`，无需动态权限（Android 10+ 分区存储友好） | 导出前检查目录可写，失败给明确提示 |

## 五、数据库初步设计

### 5.1 设计原则

三条原则贯穿整个数据模型，也是答辩时的设计亮点：

1. **三表到底，不加第四张表**。表越少，约束越清晰，查询越可解释。
2. **`study_record` 按"事件表"建模**：一行代表"某人在某天学了某个项目"，而不是"某人的学习状态"。事件表天然可追溯、可聚合出状态，且幂等由唯一约束保证。
3. **能用约束表达的规则，不写在 Java 里**。唯一性、非空、取值区间交给数据库，减少应用层判空分支。

### 5.2 E-R 关系

```
              ┌──────────────┐
              │   project    │
              │──────────────│
              │ id (PK)      │
              │ name         │
              │ category     │
              │ ...          │
              └──┬───────┬───┘
                 │1      │1
        ┌────────▼──┐  ┌─▼────────────────┐
        │ favorite  │  │  study_record    │
        │───────────│  │──────────────────│
        │ id (PK)   │  │ id (PK)          │
        │ project_id│  │ project_id (FK)  │
        │  (UNIQUE) │  │ checkin_date     │
        └───────────┘  │ (UNIQUE 组合)    │
                       └──────────────────┘
```

- `project` → `favorite`：1 : 0..1（每个项目最多被收藏一次）
- `project` → `study_record`：1 : 0..N（每个项目可有多天学习记录）

### 5.3 表结构

**表 1：`project`（非遗项目，静态预置）**

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | 主键，用于页面传参 |
| `name` | TEXT | NOT NULL UNIQUE | 项目名称，如"京剧脸谱" |
| `category` | TEXT | NOT NULL | 分类：传统技艺 / 传统美术 / 传统戏剧 / 民俗 等 |
| `region` | TEXT | — | 所属地区，如"北京" |
| `summary` | TEXT | NOT NULL | 一句话简介（列表卡片用，≤ 40 字） |
| `history` | TEXT | — | 历史渊源 |
| `craft_steps` | TEXT | — | 工序步骤，JSON 数组字符串，如 `["制胎","调漆",…]` |
| `inheritor_story` | TEXT | — | 传承人故事 |
| `cover_img` | TEXT | — | 封面图文件名（assets 内） |
| `difficulty` | INTEGER | NOT NULL DEFAULT 1，CHECK 1–3 | 难度：1 入门 / 2 进阶 / 3 挑战 |

**表 2：`favorite`（收藏）**

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | 主键 |

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|

| `project_id` | INTEGER | NOT NULL，FK→project(id) | 学习对象 |

| `quiz_score` | INTEGER | — | 当日测验得分，未测为 NULL |

| `quiz_done` | INTEGER | NOT NULL DEFAULT 0，0/1 | 是否已完成测验 |
| `updated_at` | INTEGER | NOT NULL | 最后更新时间戳 |
| — | — | **UNIQUE(project_id, checkin_date)** | 同项目同天只允许一条，幂等基石 |

### 5.4 建表语句（初稿）

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE project (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    name            TEXT    NOT NULL UNIQUE,
    category        TEXT    NOT NULL,
    region          TEXT,
    summary         TEXT    NOT NULL,
    history         TEXT,
    craft_steps     TEXT,
    inheritor_story TEXT,
    cover_img       TEXT,
    difficulty      INTEGER NOT NULL DEFAULT 1
                    CHECK (difficulty BETWEEN 1 AND 3)
);

CREATE TABLE favorite (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id INTEGER NOT NULL UNIQUE
               REFERENCES project(id) ON DELETE CASCADE,
    created_at INTEGER NOT NULL
);

CREATE TABLE study_record (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id   INTEGER NOT NULL
                 REFERENCES project(id) ON DELETE CASCADE,
    checkin_date TEXT    NOT NULL,
    quiz_score   INTEGER,
    quiz_total   INTEGER,
    quiz_done    INTEGER NOT NULL DEFAULT 0,
    updated_at   INTEGER NOT NULL,
    UNIQUE (project_id, checkin_date)
);

CREATE INDEX idx_record_date ON study_record (checkin_date);
CREATE INDEX idx_project_category ON project (category);
```

### 5.5 关键设计说明

**① 打卡去重不写在代码里**

```sql
INSERT OR IGNORE INTO study_record
    (project_id, checkin_date, quiz_done, updated_at)
VALUES (?, ?, 0, ?);
```
同一项目同一天重复点击打卡，数据库直接忽略，返回 0 行受影响。应用层无需先查后写，既避免竞态，也省一次查询。

**② 打卡日历只需一条查询**

```sql
SELECT DISTINCT checkin_date
FROM study_record
WHERE checkin_date LIKE '2026-11-%';
```
因为 `checkin_date` 是补零的 `yyyy-MM-dd`，字符串前缀匹配即等价于按月过滤，无需日期函数转换，且能命中索引。

**③ 学习进度由聚合得出，不落冗余字段**

```sql
SELECT p.id, p.name,
       COUNT(r.id)                                              AS record_cnt,
       MAX(CASE WHEN r.quiz_done = 1
                 AND r.quiz_total > 0
                 AND r.quiz_score * 1.0 / r.quiz_total >= 0.8
                THEN 1 ELSE 0 END)                              AS mastered
FROM project p
LEFT JOIN study_record r ON r.project_id = p.id
GROUP BY p.id;
```
判定规则：`record_cnt = 0` → 未开始；`mastered = 0` → 学习中；`mastered = 1` → 已掌握。**进度是查询出来的，不是存出来的**，因此不存在"状态与实际记录不一致"的隐患。

**④ 同日重复测验的覆盖策略（含 minSdk 兼容陷阱）**

同一项目当天第二次测验必须覆盖当日成绩。这里有一个容易在真机上才暴露的坑：`INSERT ... ON CONFLICT(...) DO UPDATE`（UPSERT 语法）要求 SQLite 3.24 及以上，而 **minSdk 24（Android 7.0）内置的 SQLite 只有 3.9.2**，在低版本真机上会直接抛 `SQLiteException: near "ON": syntax error`。因此统一采用兼容性最好的写法：

```sql
INSERT OR REPLACE INTO study_record
    (project_id, checkin_date, quiz_score, quiz_total, quiz_done, updated_at)
VALUES (?, ?, ?, ?, 1, ?);
```

`INSERT OR REPLACE` 的语义是"删除冲突行后插入新行"，主键 `id` 会变化；本表主键不被其他表引用，因此可安全使用。若将来业务要求保留原 `id`，改为"先 `UPDATE`，影响行数为 0 时再 `INSERT`"的两步写法。

进度聚合取 `MAX`，保证历史最好成绩不被一次低分覆盖。

**⑤ 容量与性能估算**

| 项 | 估算 | 结论 |
|---|---|---|
| `project` 行数 | 12 | 极小，可全量加载进内存 |
| `study_record` 行数 | 单人正常情况下 ≤ 12 × 365 | 千级以内，单表查询毫秒级，无需分页与优化 |
| 索引 | 2 个（`checkin_date`、`category`） | 覆盖日历与分类筛选，足够 |

### 5.6 数据初始化策略

1. 打包时把 8–12 个项目写入 `assets/projects.json`，附 `content_version`；
2. 首次启动（或 `content_version` 高于库中记录）时，子线程解析 JSON，事务内批量 `INSERT OR REPLACE`；
3. 导入过程失败则整体回滚，保留旧数据，界面提示"内容加载失败，请重试"；
4. 用户产生的 `favorite` / `study_record` **永不被内容更新清除**（外键为 `project(id)`，内容按 `name` 唯一键覆盖，不改 id）。
