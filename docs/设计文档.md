### 2.2 可行性分析

【填写要点】答辩提纲明确要求"可性能（可行性）分析"。分三块写：

- **技术可行性**：团队已掌握的 Android 技术（界面、控件、事件监听、页面跳转），本项目所需技术均在课程知识点覆盖范围内；数据库采用本地 SQLite，无需服务器
- **经济可行性**：零成本。开发工具免费，无服务器与域名支出，数据全部本地存储
- **操作可行性**：目标用户为中小学生，界面采用大卡片、大字号、少层级设计，主要操作是点击与滑动，无学习成本

【填写要点】三层：对青少年的认知价值、对非遗传播的现实价值、与课程主题的契合度。

### 3.2 总体设计

#### 3.2.1 系统架构

【填写】三层：界面层（Activity + XML）→ 逻辑层（Adapter、业务方法）→ 数据层（DBHelper/DAO + SQLite）。无网络层。

#### 3.2.2 页面流程

【填写】页面导航图：首页 →（点击卡片传 projectId）→ 详情 →（传 projectId）→ 测验 →（传 score）→ 结果；首页 → 打卡页；首页 → 我的页面

#### 3.2.3 数据库设计

【填写】三张表的 ER 图 + 字段说明。

```sql
project(id, name, category, summary, history, craft_steps,
        inheritor_story, cover_img, difficulty)

favorite(id, project_id UNIQUE, created_at)

study_record(id, project_id, checkin_date, quiz_score,
             quiz_total, quiz_done, updated_at,
             UNIQUE(project_id, checkin_date))
```

| 表 | 作用 | 关键设计 |
|---|---|---|
| project | 非遗项目内容，静态预置 | 首次启动从 assets 导入 |
| favorite | 收藏关系 | `project_id` 唯一，防重复收藏 |
| study_record | 学习记录，同时承载进度、测验、打卡 | `UNIQUE(project_id, checkin_date)` 天然去重，打卡日历靠 `SELECT DISTINCT checkin_date` |
